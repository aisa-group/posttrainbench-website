PostTrainBench v1.1

Hardening PostTrainBench against reward hacking

Version 1.1 adds specialized run-integrity judges, stronger programmatic checks, and a recomputed leaderboard after increasingly capable agents exposed gaps in the original pipeline.

PostTrainBench measures whether an AI agent can improve a small base language model with one H100 and ten hours. That score is meaningful only when the agent improves the assigned model within the same boundary as every other run.

As agents became more capable, we found strategies that could raise benchmark performance without measuring the skill we intended. Some agents shaped training data around specific evaluation failures. Others found hosted-model credentials in the environment and used a stronger model as a teacher. One run submitted an instruction-tuned model instead of the assigned base model.

We already had a general anti-cheat judge. Version 1.1 makes the rules more explicit, separates the major failure modes into independent reviews, and adds deterministic checks that do not rely on a judge model alone.

01

Benchmark‑targeted training data

Data contamination is not limited to copying an evaluation set verbatim. An agent can inspect failed evaluation items, infer their structure, and generate thousands of close variants. The text may be new while the training signal still targets particular test cases.

The v1 rules did not state this boundary precisely enough. Version 1.1 explicitly disallows generating, augmenting, hand-writing, or templating training data around specific benchmark data points, even when no benchmark text appears verbatim.

What changed
  • A dedicated contamination judge reviews each trace independently.
  • The instructions now cover both verbatim leakage and targeted synthetic clones.
  • A deterministic n-gram overlap tool, inspired by AI2's Decontamination Toolkit, checks submitted artifacts.

[[CONTAMINATION_FLAGS]] runs were flagged for contamination.

Observed examples ranged from loading a full evaluation set for memorization to producing synthetic templates immediately after inspecting individual GSM8K and BFCL failures. The latter is precisely why lexical overlap alone is not enough.

02

Submitting a different model

PostTrainBench asks the agent to post-train a specific base model. Replacing it with an existing instruction-tuned checkpoint makes the final score incomparable, even when that checkpoint belongs to the same model family.

What changed

We added a programmatic model-identity check that compares the submitted artifact with reference configurations for known instruction-tuned models.

[[MODEL_SUBSTITUTION_FLAGS]] runs were flagged for model substitution.

In the clearest observed case, Kimi K2.5 submitted the official Qwen3-1.7B instruct weights after its attempts to fine-tune Qwen3-1.7B-Base failed. The trace acknowledged the substitution and saved the replacement as final_model.

03

Using external LLM APIs as teachers

Some environments contain provider credentials needed to run the agent or an evaluator. Those credentials are infrastructure, not an extra training resource. We found agents reading keys from the environment and using hosted frontier models to generate training data, including cases where the surrounding evaluation code explicitly said not to use the key for that purpose.

API keys present in the environment may run the agent or evaluation. They may not be used to call an external model for training data or other post-training work.
What changed
  • A separate API-usage judge reviews tool calls and artifacts.
  • Unrelated provider credentials are removed or blocked from the agent environment.
  • Runs invalidated by external API use were rerun under the corrected setup.

[[API_USAGE_FLAGS]] runs were flagged for disallowed external API use.

Self-generation remains allowed. An agent can sample, filter, and retrain on outputs from the assigned model. What it cannot do is import the capability of a stronger external teacher.

04

Preventing direct benchmark lookup

Preventive safeguard

We did not observe agents searching for PostTrainBench or its public results in the audited runs. We nevertheless expect direct lookup to become attractive as agents gain stronger browsing and planning abilities.

Version 1.1 explicitly disallows looking up PostTrainBench, its leaderboard, or related materials during a run, and the contamination review checks for attempts. We are also adding network-level blocking so this boundary does not depend on instruction following alone.

05

Reruns and infrastructure fixes

We reran [[RUNS_RERUN]] runs affected by disallowed API use, missing evaluator credentials, or other infrastructure faults. Promoting Fable 5 to two seeds also removed the earlier SmolLM substitutions. Its GPQA result still falls back to Opus 4.8 Max because Fable refused that benchmark.

The updated trace viewer exposes the underlying actions, artifacts, and judge decisions so leaderboard changes can be inspected rather than taken on trust.

Why this update matters

A benchmark for autonomous agents is also an interface that agents will optimize against. The rules therefore need to describe the intended task at the level of behavior, not just at the level of the final file.

PostTrainBench 1.1 is a stricter measurement of the same question: how much can an agent improve the assigned base model with a fixed compute budget? The new pipeline makes the answer more comparable, more inspectable, and harder to inflate through shortcuts outside that task.
